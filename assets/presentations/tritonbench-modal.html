Why this exists

The premise

Triton lets you write GPU kernels in Python. LLMs can maybe write them. Question: how well, and on which kinds of operators?

The benchmark

TritonBench (THUNLP, 2025) — 184 + 166 real operators, two evaluation tracks, executable.

Our ask

A reproducible pipeline a student can launch from a laptop with one command, that costs ≈ a coffee.

Paper: arXiv:2502.14752 · Repo: github.com/thunlp/TritonBench

Two tracks: G (generate from scratch from a description) and T (translate a PyTorch function to Triton). We focus on T because it has a clean per-op golden reference and is closer to a real refactoring task.

30-second Triton refresher

  • Python DSL from OpenAI for writing custom GPU kernels.
  • One @triton.jit function ≈ one CUDA kernel, but you reason in blocks of elements, not threads.
  • Compiles via LLVM to PTX. Ships its own NVRTC.
  • Used inside PyTorch (e.g. torch.compile) and FlashAttention.

import torch, triton, triton.language as tl

@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n,
               BLOCK: tl.constexpr):
    pid  = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)
Whole point of Triton: get tensor-core-class performance without writing CUDA C++. That's exactly the kind of code we want LLMs to be able to produce.

TritonBench has two tracks

Track G

Generate from a spec

Description-only prompt. The model has to design the operator's interface AND the kernel.

Adds CodeBLEU similarity to the eval.

Track T · we use this

Translate from PyTorch

Prompt includes a working PyTorch reference (torch_code). The model rewrites it as a Triton kernel + wrapper that matches the same signature.

No similarity score — only correctness and speed.

What the LLM actually sees

An Alpaca-formatted instruction assembled from those fields:


You are an expert in Trion programming...
Functional Description: Computes the absolute value of each
element in the input tensor.
Wrapper Entry Information: abs(input_tensor, out=None) -> Tensor.
Args: input_tensor (Tensor): The input tensor...

Two things matter:

  • The model must produce a self-contained module with the same wrapper name and signature.
  • The instruction text is also the lookup key back to the reference — the eval greps the substring between "Functional Description:" and "Wrapper Entry Information:".

PyTorch reference ↔ a Triton answer

Click the card to flip. (This is what an LLM is asked to produce.)

PyTorch reference 

import torch

def abs(input_tensor, out=None):
    """Element-wise absolute value."""
    return torch.abs(input_tensor, out=out)
Triton translation 

import torch, triton, triton.language as tl

@triton.jit
def _abs_kernel(x_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid  = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, tl.abs(x), mask=mask)

def abs(input_tensor, out=None):
    n = input_tensor.numel()
    out = out if out is not None else torch.empty_like(input_tensor)
    grid = lambda meta: (triton.cdiv(n, meta['BLOCK']),)
    _abs_kernel[grid](input_tensor, out, n, BLOCK=1024)
    return out

Phase 1 — Call accuracy

Per operator: glue the LLM's code together with the embedded test driver and just try to run it as a subprocess.


file_contents = predicted_module + "\n" + ("#" * 146) + "\n" + test_driver
result = subprocess.run([python, file], capture_output=True)
ok = (result.returncode == 0)
Pass
survives → results/call_acc/abs.py
Fail
deleted (import error, kernel crash, ...)

0_call_acc.py::call_4file

The 146-character separator is upstream's convention. Test driver always starts with `def test_*` and runs at import-time.

Phase 2 — Execution accuracy

For each survivor: run the candidate AND the golden reference in two subprocesses, compare their stdout verbatim.


out1 = subprocess.run([py, llm_file], capture_output=True, text=True).stdout
out2 = subprocess.run([py, gold_file], capture_output=True, text=True).stdout
ok = (out1 == out2)   # fail → file is deleted from results/call_acc/
  • Why stdout? Each test's print(test_results) serializes the tensors, so stdout equality ≈ output equality.
  • Subtle: tiny float drift will fail. The benchmark expects bit-for-bit match for these toy ops.

1_exe_acc.py::execute_4folder

Phase 3 — Efficiency

  1. write_file.py rewrites a per-op timing harness into ./tmp/<op>_perf.py, pointing it at our surviving candidate.
  2. multiprocess_gpu_run.py launches each harness on the GPU; do_bench(warmup=100, rep=1000) records milliseconds per input size.
  3. 2_efficiency.py reads our timings + the cached golden PyTorch timings (perf_T/golden_results/) and reports speedup.

speedup_op = sum(ms_pytorch) / sum(ms_triton)         # > 1 means faster
speedup_run = mean(speedup_op for op in survivors)     # final number

Survivors with ms ≥ 10 or ≤ 0.1 are dropped as outliers (upstream rule).

Common pitfalls

T4 has no bf16 tensor cores

A handful of ops fail at phase 1 with cryptic errors. Switch to L4 or A10 by editing DEFAULT_GPU if you need them.

Instruction must match exactly

If you hand-edit the prompt, the eval can't link your prediction back to its reference. Reuse the Alpaca strings verbatim.

Speedup ≠ correctness

Phase 3 only runs over phase-2 survivors. A model with 3 fast-but-rare wins can look great until you check the passed count.

Stdout-equality is strict

Numerically-equivalent kernels can fail phase 2 due to float drift. That's the upstream rule — don't "fix" it in your fork.
